### 1.1 完整版（适合简历项目栏，约 200 字 + 要点）

> **OpenRAG Forge —— 可追溯、可组装的开源 RAG 知识库框架**（个人开源项目 / 0 → 1）
>
> 针对企业 RAG 落地中"答案无法审计、配置无法复现、安全策略形同虚设"的痛点，从既有客服 RAG 案例中抽象出通用框架：文档上传经内容感知路由解析为 Block/Chunk，拖拽式画布装配的检索链路经 Recipe Compiler 编译为带 SHA-256 哈希的不可变类型化 DAG 后才可运行，每次运行导出包含配置、模型 ID、证据、引用与安全决策的单文件 Evidence Capsule。
>
> - 设计并实现 27 类节点的类型化编译器（端口检查/环检测/规范化哈希）与 11 级 Recipe 能力阶梯（Dense 基线 → Hybrid → Rerank → 受控 Agent），画布与执行分离，发布版本不可变；

### 1.5 STAR 结构要点（面试口述版）

- **S（情境）**：此前做过一个 CFPB 客服 RAG 案例（现为 `packs/customer-support-cfpb`）。复盘发现行业通病：RAG demo 能答题，但答案无法审计——不知道哪个文档版本、哪条 chunk、哪个模型、安全策略是否生效；配置散落在代码里无法复现。
- **T（任务）**：把案例中可复用的关切抽象为通用框架，目标是三个"可"：可拆（组件即插件）、可跑（本地 30 秒起、模型离线不阻塞）、可证明（每次运行产出完整证据链），并且必须自带评测体系防止"自我感觉良好"。
- **A（行动）**：
  1. 定义核心产品对象：Recipe（编译后哈希寻址、不可变）、Evidence Capsule（单文件审计工件）、Trace（逐节点事件流）；
  2. 划定架构红线：SQLite 真相源 vs Qdrant 派生索引、编译先于执行、安全门先于生成、降级必须留痕；
  3. 建评测阶梯：单测/CI → 冒烟基准 → 带标注 Golden Eval →在线 Eval API，指标附 Wilson 区间；
  4. 首轮基准刻意保留失败结果并公开（域外误召回、引用缺失），修复后同集复测形成 before/after 证据；
  5. 领域内容（CFPB）与内核物理隔离成 Pack，验证框架可迁移到任意企业文档。
- **R（结果）**：修复后冒烟基准 4 项行为指标 1.000（7 case）；Golden Eval 检索/引用/拒答指标 1.000（附宽置信区间，如实声明非质量证明）；评测实测拦截 1 次索引脏数据；4 个单测 + 双语言 CI 常绿；产出 10+ 篇结构化文档（设计/实验/评测/路线图）。
- **（反思，主动讲）**：最大教训是先有评测才有资格迭代——首轮 0.33 的拒答正确率如果没有基准就永远不会被发现；下一步优先级是把 sparse/rerank 接真实后端并冻结 50+ case Golden Set 做 Recipe 横向对比。

## 第二部分：AI 产品经理面试准备

### 2.1 讲这个项目时的定位建议

把它讲成一个**产品判断力的展示**，而非工程秀：

1. **问题重定义**：别人卷"检索准确率"，这个项目卷"可审计性"——企业买单的是敢上线，不是 demo 好看；
2. **产品对象设计**：Recipe / Capsule / Scenario / Pack 是四个有清晰边界、可独立演进的产品单元；
3. **诚实的度量文化**：主动公开失败实验和宽置信区间，是 AI 产品经理最稀缺的素质之一；
4. **安全即产品**：拒答话术、forbidden_actions、人工审批门都是被设计出来的产品行为，不是工程副产品。

### 2.3 面试问答提纲（预演追问）

#### A. 设计决策类

- **Q：为什么要"编译"Recipe，而不是像多数低代码工具那样画布即执行？**
  A：三个产品理由：① 错误左移——非法图（端口不匹配、未声明的环）在保存时被拒绝，而不是运行到一半失败；② 不可变哈希让每个结果可归因到确切一版配置，这是审计与 A/B 的前提；③ 画布与执行分离后，画布可以随意实验而不污染已发布链路。代价是灵活性下降（不能运行任意图），这个取舍在企业场景是值得的。
- **Q：为什么 SQLite 是真相源而不是向量库？**
  A：向量库的内容是"计算结果"不是"事实"——换 embedding 模型就要重建。把可重建的东西当真相源，迁移和审计都会被锁死。实测中这个设计真的拦截过一次脏数据（评测时发现一个游离于真相源之外的 Qdrant point，被 chunk_id 过滤挡下，记录在 `docs/golden-eval-v0.1-dev.md`）。
- **Q：安全门为什么放在检索之前而不是生成之后？**
  A：高风险请求（承诺退款/认定违法/账户处置）的正确产品行为是"根本不进入生成"，事后过滤既浪费算力又有绕过风险。且拒答不是静默失败：被跳过的节点标记为 `skipped`，拒答本身也产出完整 Capsule——拒绝是需要审计的产品决策。
- **Q：为什么模型接入只做 OpenAI 兼容端点、不托管权重？**
  A：安全边界（Web 应用永不执行上传的权重文件）+ 部署解耦（LM Studio/vLLM/云端随意换）+ 可归因（Capsule 记录模型 ID）。放弃的是端到端一键体验，换来的是企业环境的可接受性。

#### B. 指标与评测类

- **Q：你的指标都是 1.000，怎么让人相信？**
  A：主动先说三点：① 样本只有 3+4/7 条，Hit@k 的 Wilson 区间下界只有 0.438，报告里就写着"这不是企业级质量声明"；② 满分证明的是"评测机制就位"而不是"系统满分"；③ 真正有信息量的数字是 before/after：0.50→1.00、0.33→1.00，那是同一测试集上被验证的修复。敢报置信区间、敢留失败记录，比报一个 92% 更可信。
- **Q：为什么选 Hit@k/MRR/nDCG 这套指标？北极星指标是什么？**
  A：分层选：检索层用排名敏感指标（MRR/nDCG）因为证据顺序影响引用质量；回答层用引用有效性/完备性（可自动测）代理"可信"；安全层独立切片测拒答正确率，防止和召回指标互相污染。当前阶段的北极星是 **可审计回答率**（有效引用且 Trace 完整的回答占比），因为它直接对应产品主张；商业化后应过渡到用户侧指标（如审计通过率、人工复核推翻率）。
- **Q：延迟 p95 8–9.6 秒能接受吗？**
  A：如实说：本地 7B 模型且有加载抖动，文档里明确不把延迟当质量声明。产品判断上，客服辅助场景（人在环）秒级可接受，面客场景不行；下一步先用 Trace 的节点级 duration 做归因，再谈优化——没有分解就谈优化是拍脑袋。

#### C. 取舍类

- **Q：引用修复回退把生成式回答换成抽取式摘要，牺牲了流畅度，怎么权衡？**
  A：合规场景里"每个事实可溯源"排在"读起来舒服"前面，这是明确的价值排序。且修复是留痕的（`citation_repaired: true`），可以统计修复率来决定是否需要换更强的模型——机制把"模型不听话"转化成了一个可度量的运营指标。
- **Q：为什么受控 Agent 不做自动执行？功能上明明可以。**
  A：客服场景动作错误的代价不对称（错发消息/错承诺退款的损失 >> 人工审批的延迟）。所以 V1 的产品边界是"只产草稿、显式列缺失字段和禁止动作、强制人工审批"。什么时候放开？当审批通过率长期稳定在高位且有回滚机制时，逐动作分级放开——这本身就是一条产品演进路线。
- **Q：做通用框架而不是垂直产品，是不是想清楚了？**
  A：诚实版本：先有垂直案例（CFPB 客服）再抽框架，路径是"从具体到抽象"，不是拍脑袋做平台。Pack 机制保留了垂直落地能力。风险我认：通用框架竞争激烈（Dify/RAGFlow），差异化押注在"编译 + 证据 + 评测内建"这条审计赛道上；如果访谈证伪这个需求，收缩回合规要求高的垂直行业是 Plan B。

#### D. 失败实验类（主动讲，别等问）

- **Q：讲一个失败的实验。**
  A：首轮冒烟基准两处失败：域外问题因停用词未过滤在词法回退路径召回了无关 chunk（检索失败）；本地模型漏掉 `[S#]` 引用且漏判英文高风险措辞（生成+安全失败）。修复方式分别是停用词+分数阈值、框架层引用修复回退、补英文正则；同集复测 0.50→1.00、0.33→1.00。教训：① 小模型的输出契约不能靠 prompt 保证，要靠框架层兜底；② 评测集里必须有"应该失败"的 case（域外/高风险），只测 happy path 的评测是装饰品。
- **Q：现在系统最大的弱点是什么？**
  A：两个：① V0.2–V0.8 的检索增强节点是编译层完整、运行层记录性的实现——图谱系是真实的，运行时增益尚未证明，这也是 roadmap P0；② 评测语料太小，所有质量结论都不外推。我把这两点直接写进了 README 的 limitations——产品经理藏短板的成本永远高于公开它。

#### E. 未来空间类

- **Q：如果给你资源，接下来三步做什么？**
  A：按 `docs/roadmap.md`：① 接通 sparse/RRF/rerank 真实后端 + 冻结 50+ case Golden Set，拿到第一份 Recipe 横向对比——这是所有质量声明的地基；② 做评测驱动闭环产品化：Recipe A/B diff、发布回归门禁、失败样本一键沉淀回 Golden Set——把"评测"从脚本变成产品功能；③ 生产 profile（Postgres/MinIO/异步 ingest/OTel）让企业试点可部署。判断依据：先补证明、再扩能力、最后扩生态。
- **Q：这个项目怎么商业化？**
  A：假设（未验证，需访谈）：买单方是合规压力大的行业（金融/医疗/政务）的 AI 平台团队；付费点不是"能检索"而是"能过审"——Evidence Capsule 对接审计流程、私有化部署、领域 Pack 与安全策略订阅。开源内核 + 商业化审计/治理层是常见且匹配的结构。这是我最想用用户访谈去证伪/证实的假设。
